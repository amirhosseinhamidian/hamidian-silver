## قرارداد فیلتر و شمارش

`POST /api/v1/catalog/public/search/facets` یک بدنهٔ JSON می‌گیرد و `items`، `total`، `totalPages`، `page`، `pageSize` و `facets` را برمی‌گرداند. بدنهٔ خالی با پیش‌فرض‌های صفحهٔ ۱ و ۲۴ محصول معتبر است.

- `scopeCategory` دسته و زیرشاخه‌های فعال آن و `scopeBrand` برند فعال را به دامنهٔ ثابت صفحه تبدیل می‌کنند. `categories` و `brands` انتخاب‌های متغیرند. انتخاب چند گزینهٔ یک Facet با OR و اتصال Facetهای متفاوت با AND انجام می‌شود. `q` از جست‌وجوی فعلی کاتالوگ استفاده می‌کند.
- شمارش هر Facet تنها انتخاب‌های همان Facet را کنار می‌گذارد. دامنهٔ ثابت صفحه و تمام فیلترهای دیگر در شمارش باقی می‌مانند. هر محصول در هر گزینه یک بار شمرده می‌شود. گزینه‌ها به‌شرط شمارش مثبت برمی‌گردند. `total` هر فیلتر فعال را اعمال می‌کند و برای صفحهٔ خارج از بازه نیز معتبر است. Sort پس از اولویت موجودی و امتیاز جست‌وجو، به شناسهٔ محصول برای ترتیب پایدار متکی است.
- سایز، طول، وزن و قیمت باید روی یک واریانت فعال و دارای موجودی خالص منطبق شوند. رزرو، انبار غیرفعال و اجزای بسته با قواعد موجود کاتالوگ محاسبه می‌شوند. قیمت پایه از قیمت مثبت واریانت یا قیمت مثبت مادر در صورت نبود قیمت واریانت به‌دست می‌آید. وزن از فیلد دقیق واریانت فعال خوانده می‌شود. برای محصول ناموجود قیمت قابل فروش در این پاسخ `null` است. انتخاب `out-of-stock` همراه با فیلتر واریانت نتیجهٔ خالی می‌دهد. بازه‌ها فقط مقادیر مشاهده‌شده و شمار محصولات متمایز را نشان می‌دهند.
- `attributes` فیلتر گزینه‌ای یا بازهٔ عددی می‌پذیرد. آخرین مقدار ثبت‌شده تحت تعریف فعال، گزینه‌های مصوب و دامنهٔ دسته اعتبار دارد. «قابل استفاده برای» از کد ثبت‌شده در Registry مانند `intended-for` و گزینه‌هایی مانند `women` استفاده می‌کند. گزینه‌ها پس از ثبت مقدار معتبر در کاتالوگ ظاهر می‌شوند. شناسهٔ تعریف یا گزینهٔ نامعتبر، بازهٔ معکوس و فیلترهای تکراری خطای ورودی‌اند.
- حداکثر ۱۶ انتخاب برای هر Facet گزینه‌ای، ۸ ویژگی فیلترشده، ۴۸ محصول در صفحه و ۱۰۰۰ صفحه مجاز است. Facetها و فهرست از همان Query و یک Snapshot خوانده می‌شوند.

## اثر روی SEO

فیلترها در بدنهٔ POST ارسال می‌شوند. پاسخ `X-Robots-Tag: noindex` دارد. URL و رفتار GET صفحات کاتالوگ، لینک HTML، HTTP/Redirect، Canonical، Robots، Sitemap و JSON-LD فروشگاه با این تغییر دست نخورده‌اند. اتصال فیلتر به رابط و بررسی انتشار در PD-02 و PD-05 پیگیری می‌شوند.

## اجرای دستی

در ریشهٔ پروژه اجرا کنید:

```bash
pnpm contracts:generate &&
pnpm contracts:typecheck &&
pnpm api:lint &&
pnpm api:typecheck &&
pnpm api:test --runInBand modules/catalog
```

برای E2E از PostgreSQL آزمایشی جداگانه استفاده کنید. اگر پایگاه داده در دسترس نیست، روش تخصیص پورت آزاد Docker در گزارش SEO-04 آمده است. [دستورهای PostgreSQL آزمایشی](SEO-04.md#بررسی-دستی)

```bash
DATABASE_URL="$PD01_TEST_DATABASE_URL" pnpm exec prisma migrate deploy &&
DATABASE_URL="$PD01_TEST_DATABASE_URL" pnpm api:test:e2e --runInBand catalog-facets
```

E2E برند بدون محصول در دامنه، حذف محصول Draft، Count محصول با چند عضویت، تطابق همهٔ فیلترها روی همان واریانت، وزن و قیمت واریانت ناموجود، نسخهٔ پاک‌شدهٔ ویژگی و صفحهٔ خارج از بازه را می‌سنجد.

برای اندازه‌گیری برنامهٔ اجرا در دیتابیس آزمایشی دارای کاتالوگ نماینده، نمونهٔ بدون جست‌وجوی متنی را اجرا کنید و Planning Time، Execution Time، Buffers و تعداد ردیف‌های میانی را ثبت کنید. Query از ایندکس‌های فعلی دسته، عضویت دسته، واریانت، موجودی و کلید نسخهٔ ویژگی استفاده می‌کند و در این تسک مهاجرت اضافه نشده است. بهره‌گیری واقعی از ایندکس‌ها و زمان پاسخ به داده و برنامهٔ اجرای PostgreSQL وابسته‌اند.

```bash
DATABASE_URL="$PD01_TEST_DATABASE_URL" pnpm exec tsx --tsconfig apps/api/tsconfig.json \
  apps/api/scripts/catalog-facets-plan.ts '{"pageSize":24,"availability":"in-stock"}'
```

مدیر پروژه موفقیت تست‌های محلی را تأیید کرد. Snapshot OpenAPI و Typeهای مصرف‌کننده پس از تولید قرارداد به‌روز شدند. نتیجهٔ E2E PostgreSQL و Query Plan روی دادهٔ نماینده در انتظار ثبت است.
