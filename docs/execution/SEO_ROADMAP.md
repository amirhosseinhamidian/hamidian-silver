## چشم‌انداز و اصل طراحی

ابتدا مشکلات فنی واقعی کشف و اصلاح می‌شوند؛ سپس لایه‌های جمع‌آوری داده و داشبورد روی پایه قابل اتکا ساخته می‌شوند.

هر تسک یک واحد تحویل مستقل با دامنه روشن، تست‌های ضروری و معیار پذیرش است؛ کاهش تعداد تسک‌ها به معنی حذف کنترل کیفیت نیست.

اطلاعات رسمی گوگل، نتیجه بررسی داخلی سایت و نتیجه تست زنده هر URL با برچسب‌های مجزا نمایش داده می‌شوند؛ هیچ‌کدام به‌جای دیگری ارائه نمی‌شود.

اقدامات حساس مانند تغییر Robots، Canonical، Noindex و انتشار محتوا فقط پس از بررسی و تأیید مسئول سیستم انجام می‌شوند.

## ۱. مسئله، دامنه و معیارهای موفقیت

گزارش‌های اولیه Search Console نشان دادند که شمار قابل‌توجهی از محصولات در وضعیت «Discovered – currently not indexed» قرار گرفته‌اند؛ در عین حال Sitemap خوانده شده و Googlebot موفق به دریافت بسیاری از صفحات HTML شده است. درخواست‌های مرتبط با RSC نیز سهم چشمگیری از خزش نخستین دوره فعالیت داشته‌اند. این‌ها نشانه‌های قابل بررسی‌اند، نه اثبات وجود یک خطای سراسری یا محدودیت قطعی بودجه خزش.

مسئله اصلی فقط ایندکس شدن URLها نیست. فروشگاه باید بتواند عملکرد صفحات را در جست‌وجوهای غیربرندی اندازه‌گیری کند، مشکلات فنی را زود تشخیص دهد و تلاش‌های تولید محتوا و ثبت محصول را با فرصت‌های واقعی جست‌وجو هماهنگ کند.

### SEO-01 — ممیزی جامع Technical SEO

هدف تسک: شناخت رفتار واقعی کد و HTML خروجی، تفکیک خطاهای تأییدشده از فرضیه‌ها و تولید بک‌لاگ اصلاحات با اولویت روشن.

#### شرح اجرایی

ساختار فعلی Monorepo و مسیرهای SEO در storefront، API، Prisma و سرویس‌های پس‌زمینه بررسی شود؛ مسیر دقیق فایل‌های مسئول Sitemap، robots، metadata و صفحات محصول ثبت شود.

برای صفحات محصول، دسته‌بندی، برند و دانستنی‌ها، رفتار HTTP، رندر سرور، Meta Robots، Canonical، Title، Description و کد وضعیت نمونه‌برداری و مستند شود.

لینک‌های HTML واقعی از فهرست، دسته‌بندی، برند و محصولات مرتبط بررسی شوند؛ نمونه مسیرهای خراب مانند تکرار /products/ یا مسیر نادرست دانستنی‌ها ریشه‌یابی شود.

قوانین Noindex برای محصولات ناموجود، مخفی، پیش‌نویس، صفحه‌بندی و URLهای پارامتردار با وضعیت انتشار محصول و منطق سئو تطبیق یابد.

خروجی Sitemap، lastmod، آدرس تصاویر، canonical و صفحات قابل ایندکس با یکدیگر مقایسه شوند؛ حضور URL در Sitemap با ایندکس شدن اشتباه گرفته نشود.

Product، Merchant Listing و Breadcrumb structured data در نمونه صفحات معتبرسنجی و هشدارهای غیرحیاتی از خطاهای مؤثر تفکیک شوند.

درخواست‌های RSC، Prefetch و Googlebot بر اساس لاگ‌ها و خروجی خزش تحلیل شوند، بدون فرض قبلی مبنی بر زیان‌بار بودن تمام درخواست‌های _rsc.

از URLهای Discovered و Crawled-not-indexed نمونه‌گیری شود و برای هر نتیجه سطح اطمینان، تاریخ داده و شواهد مشخص گردد.

#### خروجی‌های قابل تحویل

گزارش ممیزی شامل شناسه، شدت، شواهد بازتولید و مسیرهای کد مرتبط با هر یافته.

فهرست اولویت اصلاحات با تفکیک «باگ قطعی»، «ریسک» و «فرضیه نیازمند بررسی».

#### معیارهای پذیرش و کنترل کیفیت

برای هر خطای P0/P1 روش بازتولید وجود داشته باشد.

گزارش به‌صراحت مشخص کند کدام شواهد از Search Console و کدام از تست زنده/کد هستند.

بدون تغییر در محیط Production و بدون ثبت خودکار درخواست ایندکس پایان یابد.

وابستگی و نکته اجرایی: این تسک پیش‌نیاز SEO-02 و مرجع تصمیم‌گیری کل پروژه است.

### SEO-02 — اصلاح مشکلات و تثبیت زیرساخت SEO

هدف تسک: رفع دسته‌بندی‌شده خطاهای اثبات‌شده در SEO-01 و ایجاد حفاظت آزمونی در برابر بازگشت آن‌ها.

#### شرح اجرایی

اصلاح منبع تولید لینک‌های اشتباه، مسیرهای تکراری و Redirectهای ناسالم؛ حفظ URLهای معتبر قبلی و طراحی Redirect فقط در صورت ضرورت.

یکسان‌سازی منطق Canonical و Robots برای انواع موجودیت‌ها و وضعیت‌های انتشار؛ مسیر اصلی محصول و نسخه‌های دارای پارامتر صریحاً تست شوند.

اصلاح تولید Sitemap بر مبنای وضعیت انتشار و قواعد قابل ایندکس بودن، با URL و lastmod پایدار و معتبر؛ ثبت صفحات کم‌ارزش به‌طور تصادفی جلوگیری شود.

در صورت تأیید مشکل، لینک‌های HTML قابل خزش میان دسته‌بندی‌ها، برندها و محصولات بهبود یابند؛ صفحه‌بندی و دسترسی به محصولات عمیق کنترل شود.

خطاهای جدی در Schema، وضعیت HTTP یا متادیتا با رعایت معماری جاری اصلاح شوند؛ موارد غیربحرانی مستقل از مانع ایندکس گزارش شوند.

Prefetch تنها روی مسیرهای اثباتاً غیرضروری یا پُرهزینه تنظیم شود؛ مسدودسازی کلی RSC، JavaScript یا CSS در robots.txt ممنوع باشد مگر پس از ارزیابی مستند.

تست Unit و Integration برای توابع تولید URL، Metadata، Sitemap و قواعد Indexability و تست E2E برای مسیرهای اصلی ایجاد یا تکمیل شود.

#### خروجی‌های قابل تحویل

اصلاحات کوچک و قابل مرور در فایل‌های واقعی پروژه.

مجموعه تست‌های رگرسیون و یادداشت تغییر رفتار SEO و مسیر بازگشت.

#### معیارهای پذیرش و کنترل کیفیت

نمونه URLهای استاندارد پاسخ مورد انتظار، Canonical صحیح و Robots مناسب داشته باشند.

مقایسه قبل/بعد نشان دهد اصلاحات آسیبی به صفحات سالم نزده‌اند.

CI موفق باشد و اثر تغییرات روی صفحات فهرست، جزئیات محصول، برند و مقاله بررسی شود.

وابستگی و نکته اجرایی: فقط یافته‌های اثبات‌شده SEO-01 اجرا شوند؛ تغییرات بهینه‌سازی حدسی باید جدا و با معیار سنجش مطرح شوند.

### SEO-03 — اتصال امن Google Search Console API

هدف تسک: ساخت یک لایه یکپارچه، امن و تست‌پذیر برای دریافت داده‌های جست‌وجو و Sitemap.

#### شرح اجرایی

Property متعلق به hamidian.shop و روش احراز هویت مناسب برای سرور انتخاب و مجوز حداقلی Read-only اعمال شود؛ کلیدها یا Tokenها در Frontend منتشر نشوند.

Client ماژولار برای Search Analytics API با ابعاد date، query، page، device و search type و امکان فیلتر/صفحه‌بندی داده پیاده شود.

Clicks، Impressions، CTR و Average Position با واحدها و قواعد تجمیع صحیح وارد شوند؛ جمع سطرهای Query با مجموع Property به‌اشتباه برابر فرض نشود.

عملکرد برند/غیربرند در صورت پشتیبانی API مربوط دریافت شود؛ در غیر این صورت روش برآورد مبتنی بر Query با برچسب «تخمینی» و محدودیت داده تعریف شود.

وضعیت Sitemap از API مربوط دریافت شود و محدودیت آن در ارائه فهرست کامل ایندکس مستند گردد.

محدودیت Rate Limit، پاسخ‌های 401/403/429/5xx، Retry با Backoff، Timeouts، لغو مجوز و خطای Property در یک لایه مشترک کنترل شود.

سرویس‌ها صرفاً از API داخلی مجاز فراخوانی شوند و دسترسی تنظیمات اتصال به نقش‌های ادمین محدود باشد.

#### خروجی‌های قابل تحویل

سرویس مستقل NestJS با Interface قابل Mock و مستندات تنظیم Google Cloud.

Endpointهای مدیریت وضعیت اتصال و دریافت داده با دسترسی کنترل‌شده.

#### معیارهای پذیرش و کنترل کیفیت

خواندن واقعی Performance و Sitemaps در محیط مجاز موفق باشد.

Token، Client Secret و جزئیات حساس در Log و پاسخ API ظاهر نشوند.

خطاهای دسترسی، سهمیه و قطع اتصال با وضعیت قابل فهم و قابل بازیابی مدیریت شوند.

وابستگی و نکته اجرایی: ورودی SEO-04؛ قرارداد این سرویس نباید مستقیماً به ساختار UI گره بخورد.

### SEO-04 — مدل داده، تاریخچه و همگام‌سازی خودکار

هدف تسک: تبدیل پاسخ‌های API به داده تاریخی قابل مقایسه با قابلیت راه‌اندازی مجدد بدون فساد یا تکرار.

#### شرح اجرایی

مدل‌های Prisma برای Integration، SyncRun، PerformanceDaily، UrlInventory و داده‌های ارتباطی با Product/Category/Article طراحی شوند؛ از تکرار کاتالوگ جلوگیری شود.

کلیدهای یکتا برای ابعاد متریک (تاریخ، Property، نوع جست‌وجو، دستگاه، Query/Page و سایر فیلترها) تعریف شود تا Upsert دقیق و idempotent باشد.

Job همگام‌سازی دوره‌ای با صف/قفل اجرای هم‌زمان و کنترل بار VPS ساخته شود؛ Backfill تاریخی محدود به داده‌های در دسترس API باشد.

چند روز اخیر در هر اجرا دوباره همگام شوند تا تأخیر ثبت داده‌های Google Search Console پوشش داده شود؛ تاریخچه Sync و نسخه داده ثبت شود.

URLها نرمال‌سازی شوند، اما مسیر اصلی، Query parameter و URL گزارش‌شده توسط گوگل قابل ردگیری بمانند؛ ارتباط به Product ID با قواعد قابل تست انجام شود.

محاسبات تجمیعی CTR و Average Position با وزن Impressions انجام شوند و داده‌های ناقص یا پنهان‌شده گوگل به‌عنوان صفر واقعی تعبیر نشوند.

تست Migration، Rollback عملیاتی، Retry، اجرای هم‌زمان، قطع ارتباط و عدم تکرار رکورد انجام شود.

#### خروجی‌های قابل تحویل

جداول و Migrationهای Prisma با راهنمای Deploy.

Background Job قابل مشاهده با تاریخ آخرین Sync، وضعیت، تعداد ردیف و خطا.

تاریخچه متریک قابل استفاده برای API داشبورد.

#### معیارهای پذیرش و کنترل کیفیت

اجرای دوباره Sync خروجی تکراری ایجاد نکند و داده‌های معتبر قبلی را حذف نکند.

توقف و راه‌اندازی مجدد Worker موجب از بین رفتن Job یا پردازش نادرست نشود.

داده‌های یک بازه نمونه با خروجی همان API و سطح ابعاد یکسان تطبیق داده شوند.

وابستگی و نکته اجرایی: به SEO-03 متکی است؛ خروجی آن مبنای تمام صفحات P2 و موتور هشدار P4 است.

### SEO-05 — داشبورد اصلی و تحلیل عملکرد جست‌وجو

هدف تسک: ارائه دید سریع از رشد و افت ترافیک ارگانیک، بدون نیاز به دانلود فایل یا ورود روزانه به Search Console.

#### شرح اجرایی

نمای Overview برای Clicks، Impressions، CTR و Average Position ساخته شود و مقایسه دوره انتخابی با دوره هم‌طول قبلی انجام شود.

نمودارهای روزانه و هفتگی همراه با حالت Loading، Empty، Error و داده ناقص ارائه شوند؛ تاریخ آخرین Sync در نما آشکار باشد.

فیلترهای بازه تاریخ، Search type، Device و Branded/Non-branded (در صورت وجود داده قابل اتکا) پیاده شوند.

جداول Query و Page با فیلتر، جست‌وجو، مرتب‌سازی و صفحه‌بندی سروری ساخته شوند؛ خروجی CSV در صورت نیاز مجاز باشد.

در مقایسه وضعیت Property و جمع سطرهای Query/Page از نمایش اختلاف به‌عنوان خطای محاسبه اجتناب شود؛ منشأ و محدودیت داده توضیح داده شود.

APIهای Admin با کنترل سطح دسترسی، Cache محدود و Pagination مناسب برای چند هزار URL طراحی شوند.

رابط کاربری واکنش‌گرا و هماهنگ با Design System فعلی ساخته شود؛ اعداد فارسی، برچسب‌ها و متن رابط در محیط فارسی خوانا باشند.

#### خروجی‌های قابل تحویل

صفحه SEO Overview و APIهای Aggregation.

نمودارها و جداول عملکرد با فیلتر و وضعیت به‌روزرسانی.

#### معیارهای پذیرش و کنترل کیفیت

مدیر بتواند یک دوره را انتخاب و تغییر عملکرد نسبت به دوره قبل را صحیح مشاهده کند.

نمایش بدون داده و در زمان خطای Sync صادقانه و شفاف باشد.

تست E2E گردش انتخاب فیلتر، مشاهده نتیجه و کنترل مجوز دسترسی موفق باشد.

وابستگی و نکته اجرایی: به SEO-03 و SEO-04 متکی است؛ نقطه شروع تحویل MVP مدیریتی.

### SEO-06 — تحلیل سئوی محصولات، دسته‌بندی‌ها و مقالات

هدف تسک: تبدیل داده صفحه‌محور گوگل به تحلیل قابل اقدام برای واحدهای اصلی کسب‌وکار.

#### شرح اجرایی

صفحه عملکرد برای Product، Category، Brand و Guide Article بر اساس URL اصلی و شناسه داخلی موجودیت طراحی شود.

برای هر صفحه، روند کلیک/نمایش، Queryهای مهم، Device و وضعیت تغییرات نسبت به دوره قبل نمایش داده شود.

صفحات با نمایش زیاد و CTR کم، افت کلیک یا رشد سریع فقط با معیارهای دارای حداقل حجم داده فهرست شوند؛ آستانه‌ها قابل تنظیم باشند.

صفحات با داده جست‌وجوی ناکافی به‌صورت «داده کافی موجود نیست» نشان داده شوند، نه با رتبه صفر یا امتیاز ساختگی.

از صفحه تحلیل سئو به ویرایش همان محصول، دسته‌بندی یا مقاله در Admin لینک عملیاتی وجود داشته باشد.

برای صفحات دارای پارامتر، وضعیت Canonical و قواعد اتصال به موجودیت ثبت شود و متریک‌ها بدون ادغام اشتباه تجمیع شوند.

تست کارکرد برای موجودیت حذف‌شده، URL تغییرکرده، چند URL مرتبط و فقدان داده Query نوشته شود.

#### خروجی‌های قابل تحویل

نمای جزئیات سئو برای هر نوع محتوای مهم.

جداول فرصت‌های عملکردی با امکان رفتن به فرم ویرایش مربوط.

#### معیارهای پذیرش و کنترل کیفیت

آمار هر صفحه با همان ابعاد در منبع داده تطبیق‌پذیر باشد.

صفحات کم‌داده برچسب مناسب داشته باشند و رتبه یا CTR نادرست تولید نشود.

مدیر بتواند از داشبورد به صفحه مدیریت محتوای مرتبط برود.

وابستگی و نکته اجرایی: به SEO-05 و جدول UrlInventory وابسته است؛ تکمیل آن پایان MVP داشبورد است.

## ۲.4 فاز P3 — پایش ایندکس و سلامت فنی

### SEO-07 — موتور خودکار Technical SEO Audit

هدف تسک: تشخیص مشکلات قابل اندازه‌گیری در سایت خودمان پیش از گسترش آن‌ها میان چند هزار محصول.

#### شرح اجرایی

فهرست URLهای قابل بررسی از محصولات منتشرشده، دسته‌بندی‌ها، برندها، مقالات و Sitemap ساخته شود؛ اولویت بر اساس اهمیت تجاری و وضعیت اخیر باشد.

Crawler سبک و محدود به دامنه‌های مجاز با Timeouts، Rate Limit، Concurrency پایین و سقف درخواست طراحی شود.

برای هر URL، HTTP status، Redirect chain، Canonical، Meta Robots، Title، Description و عناصر اصلی Schema از HTML واقعی استخراج شود.

قواعد تضاد مانند «URL در Sitemap اما Noindex»، «Canonical به صفحه نامرتبط» یا «محصول موجود با پاسخ 404» به صورت Ruleهای قابل تست ثبت شوند.

لینک‌های داخلی شکسته، وضعیت دسترسی به محصولات عمیق و مشکلات معمول صفحه‌بندی به‌صورت نمونه‌برداری یا تحلیل گراف سبک بررسی شوند.

محتوای مشابه صرفاً نشانه‌گذاری شود؛ تشخیص تکراری بودن نیازمند معیارهای روشن و بازبینی انسانی است.

نتیجه هر Audit شامل زمان اجرا، نسخه Rule، نوع خطا، شواهد و وضعیت اولیه/جدید ذخیره شود.

در طراحی از درخواست‌های گسترده و هم‌زمان که روی VPS فروشگاه یا دیتابیس عملیاتی فشار ایجاد می‌کنند، جلوگیری شود.

#### خروجی‌های قابل تحویل

SEO Audit Worker و Rule Engine داخلی.

جدول نتایج و تاریخچه سلامت فنی URLها.

نمای Technical Issues برای شناسایی URLهای مسئله‌دار.

#### معیارهای پذیرش و کنترل کیفیت

اسکن محدود نمونه‌های معتبر، Redirect، Noindex و 404 نتایج درست تولید کند.

Job در قطع شبکه یا Restart قابل بازیابی باشد و Rate Limit داخلی را رعایت کند.

هیچ Rule بدون شواهد قابل مشاهده به‌عنوان خطای قطعی نمایش داده نشود.

وابستگی و نکته اجرایی: از P1 برای ذخیره‌سازی و از P0 برای قواعد صحیح سئوی پروژه استفاده می‌کند.

### SEO-08 — پایش ایندکس و تطبیق داده‌های گوگل

هدف تسک: نمایش وضعیت ثبت‌شده URL در Google Index همراه با تفکیک دقیق آن از سلامت فنی زنده.

#### شرح اجرایی

Client مربوط به URL Inspection API با کنترل سهمیه و خطا طراحی شود و URLهای اولویت‌دار بر اساس عملکرد، تغییرات محتوا و مشکلات قبلی انتخاب شوند.

وضعیت Indexing، Coverage، Canonical انتخاب‌شده توسط گوگل، تاریخ آخرین خزش (اگر موجود است) و نتیجه API با Timestamp ثبت شود.

در داشبورد، «وضعیت گوگل»، «وضعیت بررسی فنی سایت» و «حضور در Sitemap» در ستون‌های مستقل نمایش داده شوند.

ورود کنترل‌شده CSV/ZIP خروجی Coverage و Drilldown برای تحلیل گروهی در صورت نیاز فراهم شود؛ قالب و داده ورودی اعتبارسنجی شوند.

فرایند نمونه‌برداری، چرخش اولویت و جلوگیری از بررسی مکرر URLهای کم‌اهمیت طراحی شود؛ سهمیه API قابل مشاهده باشد.

نتیجه Inspection معادل تست زنده یا درخواست ایندکس فرض نشود و تاریخ داده قدیمی یا ناقص در UI مشخص باشد.

اختلاف‌هایی مانند «HTML 200 اما Unknown/Discovered» به‌عنوان مورد نیازمند بررسی ثبت شوند، نه به‌عنوان خطای قطعی سایت.

#### خروجی‌های قابل تحویل

Index Monitoring با وضعیت تاریخ‌دار و قابل مقایسه.

صف بررسی URLهای اولویت‌دار و ورود خروجی Coverage.

گزارش اختلاف میان وضعیت محلی و وضعیت ثبت‌شده گوگل.

#### معیارهای پذیرش و کنترل کیفیت

هیچ وضعیت ایندکس بدون زمان و منبع گزارش نشود.

در صورت پایان سهمیه، سیستم متوقف و با پیام صحیح بازیابی شود.

URL Inspection با Live Test یا درخواست Indexing اشتباه گرفته نشود.

وابستگی و نکته اجرایی: به SEO-03، SEO-04 و SEO-07 متکی است؛ داده ورودی هشدارهای ایندکس در P4 را ایجاد می‌کند.

### SEO-09 — موتور هشدار و مدیریت مشکلات سئو

هدف تسک: شناسایی به‌موقع افت عملکرد یا تغییرات فنی و ایجاد چرخه رسیدگی تا رفع کامل.

#### شرح اجرایی

Ruleهای هشدار برای افت غیرعادی کلیک/نمایش، خطای فنی جدید، تغییر Canonical/Noindex و وضعیت ایندکس صفحات مهم تعریف شوند.

آستانه‌ها بر مبنای حداقل حجم داده، بازه مقایسه و سطح اهمیت صفحه تنظیم شوند تا نوسان طبیعی به هشدار کاذب تبدیل نشود.

کلید Deduplication و دوره آرام‌سازی برای هشدارهای تکراری طراحی شود؛ تغییر شدت یا بازگشت مشکل رویداد مستقل ایجاد کند.

هشدارهای منتخب از سیستم اعلان موجود Admin/Telegram ارسال شوند؛ خطای کانال اطلاع‌رسانی مانع ثبت Issue اصلی نشود.

هر هشدار لینک مستقیم به URL، گزارش فنی، Query/Page یا رخداد Sync مربوطه داشته باشد.

تست نویز، مرزبندی آستانه‌ها، خطای اتصال و جلوگیری از ارسال تکراری اعلان انجام شود.

Rule Engine هشدار، صندوق Issues و تاریخچه اقدامات.

وابستگی و نکته اجرایی: به P1 و P3 متکی است؛ اعلان‌ها باید قابلیت‌های موجود فروشگاه را بازاستفاده کنند.

### SEO-10 — موتور تحلیل فرصت‌ها و پیشنهادهای هوشمند

محصولات و دسته‌ها با ترکیبی از فرصت جست‌وجو، موجودی، اهمیت تجاری و کیفیت داده اولویت‌بندی شوند؛ فرمول و وزن‌ها نسخه‌دار باشند.

پیشنهادهای قابل اقدام برای عنوان، توضیحات، لینک‌سازی داخلی، ساختار محتوا و ارتباط مقالات با دسته‌بندی‌ها تولید شوند.

در صورت استفاده از AI، اطلاعات ورودی حداقلی و امن باشد؛ پیشنهاد با شواهد داده‌ای، عدم قطعیت و محدودیت‌های منبع همراه شود.

مدیر بتواند هر پیشنهاد را تأیید، رد، تعویق یا به تسک اصلاحی تبدیل کند؛ اعمال خودکار تغییر محتوای سایت در محدوده این نسخه نیست.

برای پیشنهادهای اجراشده، بازه پیش/پس و عوامل مداخله‌گر ثبت شوند؛ افزایش کلیک را بدون شواهد به تغییر انجام‌شده نسبت ندهیم.

پیشنهادهای تکراری یا ناسازگار با قواعد نام‌گذاری و SEO فروشگاه فیلتر شوند.

## ۳. معماری هدف و مرزبندی مسئولیت‌ها

ماژول SEO باید با سیستم فعلی فروشگاه یکپارچه باشد، اما مسئولیت‌های جمع‌آوری داده، تجمیع، پایش فنی و نمایش را از یکدیگر جدا کند. پیاده‌سازی مستقل یک کاتالوگ محصول، موتور احراز هویت موازی یا Worker جدید بدون نیاز اثبات‌شده، برخلاف هدف نگهداری‌پذیری پروژه است.

## اصول طراحی داده

رکوردهای Performance به ابعاد دقیق Query/Page/Device/Search Type و تاریخ وابسته‌اند؛ جمع زدن CTR یا Average Position به‌صورت میانگین ساده مجاز نیست.

هر داده گوگل باید Property، بازه، منبع API و زمان دریافت مشخص داشته باشد.

وضعیت ذخیره‌شده Index Inspection ممکن است از وضعیت زنده سایت عقب باشد؛ UI این فاصله را پنهان نمی‌کند.

شناسه محصول یا مقاله از مدل‌های اصلی فروشگاه ارجاع داده شود و تغییر URL به‌صورت تاریخچه/نگاشت قابل رهگیری باشد.

Jobs با قفل، شناسه اجرا، ثبت خطا، قابلیت Retry و کنترل هم‌زمانی طراحی شوند.

داده ورودی CSV/ZIP و پاسخ‌های خارجی اعتبارسنجی شوند؛ محتوای برون‌سامانه‌ای دستور اجرایی محسوب نشود.

ارسال داده به سرویس AI باید حداقلی، مجاز، و بدون Secret یا اطلاعات خصوصی کاربران باشد.

## پایداری و کارایی

همگام‌سازی و Audit فشار کنترل‌نشده بر VPS، PostgreSQL، CDN یا API گوگل ایجاد نکنند.

Timeout، Backoff، Rate Limit، Idempotency و ثبت وضعیت عملیات در Jobهای طولانی الزامی است.

تغییر Schema باید Migration قابل ارزیابی و برنامه بازگشت داشته باشد.

فهرست‌ها و نمودارها از Pagination و فیلتر سمت سرور استفاده کنند.

## تست و پذیرش

Unit Test برای قواعد SEO، نرمال‌سازی URL، تجمیع متریک و قوانین هشدار.

Integration Test برای APIهای Google (با Mock قراردادی)، Prisma و سرویس‌های Job.

E2E Test برای مسیرهای حیاتی Admin و سئوی صفحات اصلی فروشگاه.

مرور اثر روی صفحات سالم، مقایسه قبل/بعد و موفق بودن CI پیش از ادغام.

ثبت مستند تغییرات، فرضیات و محدودیت‌ها در انتهای هر تسک.

## ۷. روش اجرای هر تسک در مخزن

Inspect: مطالعه مسیرهای کد و تست‌های موجود، ثبت مفروضات و تفکیک باگ قطعی از فرضیه.

Design: انتخاب کم‌هزینه‌ترین تغییر سازگار با معماری موجود و مشخص کردن قراردادهای API/DB.

Implement: انجام تغییرات کوچک، قابل مرور و با قابلیت بازگشت.

Validate: اجرای تست‌های مرتبط، تحلیل اثر روی صفحات موجود و کنترل خطاهای محیط.

Review: بازبینی امنیت، داده، عملکرد و اثرات جانبی SEO.

Commit & CI: ثبت تغییرات همراه با توضیح و پذیرش پس از موفقیت Pipeline.

Acceptance: ثبت خروجی، شواهد تست، محدودیت‌ها و موارد باقی‌مانده.

این چرخه درون همان ۱۰ تسک انجام می‌شود. تقسیم داخلی یک تسک به چند Commit یا چند اجرای Codex مانعی ندارد؛ اما ساخت تسک‌های مستقل اضافی فقط در صورت تغییر دامنه یا وجود وابستگی جدید انجام شود.
